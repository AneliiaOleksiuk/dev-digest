# Development Plan: SPEC-02 Onboarding Generator

Spec: [specs/SPEC-02-onboarding-generator.md](../../specs/SPEC-02-onboarding-generator.md)
(read in full; it is the authoritative requirements source — this plan does not
restate its 39 ACs, 19 edge cases or 14 decisions, it maps work items onto them).

## Objective

Turn the already-shipped-but-unwired onboarding scaffolding — an `onboarding`
table nothing writes, `Onboarding*` contracts nothing uses, a `FEATURE_MODELS`
slot nothing resolves, a system prompt nothing loads, and two `repoIntel` facade
methods nothing calls — into one repo-scoped page that shows five grounded
sections for a repo, generated by **exactly one** structured LLM call on an
explicit, confirmed user action, with the call's cost recorded and every path and
command verified in code before it is persisted.

This is wiring plus product decisions, not new machinery: no new pipeline stage,
no new facade method, no `reviewer-core` change.

## Scope

- **Packages/modules touched:** `server/` (new `src/modules/onboarding/`,
  `src/db/schema/context.ts` + a generated migration, `src/platform/container.ts`,
  `src/modules/index.ts`, `src/prompts/onboarding.system.md`,
  `src/vendor/shared/contracts/knowledge.ts`), `client/` (new
  `/repos/[repoId]/onboarding` route, `src/lib/hooks/`, `src/lib/types.ts`,
  `src/components/app-shell/helpers.ts`, `messages/en/onboarding.json`,
  `src/vendor/ui/nav.ts`, `src/vendor/shared/contracts/knowledge.ts`).
- **Execution mode:** **multi-agent (full handoff chain)** — `implementer` →
  `test-writer` → `plan-verifier` → `doc-writer`, each a separate invocation.
  **Assumed, not confirmed:** `AskUserQuestion` is unavailable inside a subagent,
  so this mirrors the SPEC-01 delta plan's mode as the user indicated to expect.
  Test authorship, spec/architecture verification and documentation are therefore
  **not** work items here; each work item's Definition of done names the test that
  must exist so `test-writer` and `plan-verifier` can trace it, but writing it is
  their job. **If the user chooses single-agent instead**, this section and
  `Explicitly out of scope` must be amended and per-item test-writing plus a
  final self-verification item added before `implementer` starts.
- **Explicitly out of scope (feature-level, from the Spec's Non-goals):**
  `reviewer-core/**` (untouched — this call does not go through `assemblePrompt`);
  re-indexing / any new pipeline stage / any new `repoIntel` facade method;
  chunking, embeddings, retrieval (`code_chunks`); more than one LLM call per
  generation (no per-section call, no map-reduce, no refinement, no auto-retry
  beyond the provider adapter's own `maxRetries`); per-user tours or tour history;
  in-app tour editing; feeding the tour into review prompts (`PromptParts`,
  `run-executor.ts` unchanged); a shared/access-controlled tour URL; deepening the
  clone for churn/hotness; auto-generation on import, resync or page load;
  `mcp/` + pre-push CLI parity; an in-app source viewer; `e2e/`.

## Recommendations

Concrete enough to act on or reject. Items 1–4 are decisions this plan makes on
the Spec's explicit invitation ("a Development Plan choice"); item 5 is a risk the
Spec did not call out.

1. **Generation metadata goes in new columns, not inside `onboarding.json`.**
   The Spec leaves this open. Columns win because AC-36 requires the stored
   `json` to be parsed against the `Onboarding` contract
   (`knowledge.ts:44-47` = `{sections}`) on read as well as write — a zod object
   strips unknown keys, so metadata smuggled into `json` would be silently lost
   by the very validation AC-36 mandates, or force a `.passthrough()` hack. New
   columns also keep `generated_at` (`context.ts:125`) company at the same level
   and make AC-26's sha comparison a column read, not a JSON dig. Cost: one
   `pnpm db:generate` migration (WI2). Reject this and WI2 collapses into WI1,
   but AC-36 then needs a different answer.
2. **Generation runs inline on the request, not through `JobRunner`.** The Spec
   makes this an implementation choice with one observable requirement (progress
   shown, AC-27 guard holds either way). Inline: no new job kind, no status
   endpoint, no client polling hook; progress is the react-query mutation's
   `isPending`; the AC-27 guard is an in-process `Map<repoId, Promise>` in the
   service — which the Spec already forces to live in the feature ("rate limiting
   is fully disabled under `NODE_ENV=test`, so the concurrency guard must be
   enforced in the feature"), and which is consistent with `server/AGENTS.md`'s
   already-documented single-API-process assumption (`reapStaleRuns()`). Going
   through `JobRunner` would also make its 120 s hard budget
   (`repo-intel/constants.ts:47`) the de-facto answer to the still-open Q9 without
   a product decision — see Risks.
3. **E-7 (monorepo, several `package.json` files) gets an explicit deterministic
   rule, since the Spec requires determinism and attribution but names no rule:**
   read the root `package.json`, plus every `package.json` at depth ≤ 2 sorted
   by path, capped at `MAX_RUN_LOCALLY_SOURCES` (5, WI4's constant). Each
   surviving command is attributed to the exact file it came from (AC-34, UX-8).
   This repo is itself the case: five packages, no workspace.
4. **E-4 (flat/degenerate ranking) is detectable today — use the facade, don't
   invent a heuristic.** `repoIntel.getFileRank(repoId, paths)` returns
   `{path, percentile}` (`repo-intel/service.ts:456-461`,
   `types.ts:127-130`) and `computeFileRank` gives every file the same uniform
   score on a degenerate graph (`pipeline/rank.ts:39-47`, ties share a percentile
   value). So: if the sampled top paths yield ≤ 1 distinct percentile, the reading
   path must be presented as "no import-graph signal" rather than as importance
   order. The same percentiles are the deterministic signal AC-12/UX-5 offer as
   the alternative to labelling the First-tasks badge a model estimate — pick one
   in WI11 and say which.
5. **Risk the Spec doesn't call out: the pre-existing `activeKeyFor` already
   routes `/onboarding` to the tour's nav key.**
   `client/src/components/app-shell/helpers.ts:29` reads
   `if (pathname.includes("/onboarding")) return "onboarding-tour";` — so the
   moment a nav item with key `onboarding-tour` exists, the **add-repo** screen at
   `/onboarding` (`client/src/app/onboarding/page.tsx`) will highlight the
   Onboarding Tour sidebar item. That is E-17's comprehension hazard arriving
   through a file the Spec never mentions. WI10 must fix the predicate (exact
   `/onboarding` → no tour key) as part of the nav work, not leave it.

**WI9 — Persist, replace atomically, guard concurrency, record usage, log.**

counts and sizes, model, tokens and cost — **never** file contents, the assembled

## Risks / Open questions

- **Q9 — latency and timeout targets are unresolved, and this plan does not
  invent one.** No page-load target, no generation-latency target and no value
  for `StructuredRequest.timeoutMs` (`vendor/shared/adapters.ts:62`) has been
  agreed. WI6 therefore leaves `timeoutMs` **unset**, which inherits the LLM
  adapters' pre-existing `DEFAULT_TIMEOUT` of 60 s
  (`adapters/llm/openai.ts:15`, `adapters/llm/anthropic.ts:16`) — an existing
  default being relied on, not a threshold chosen here. `implementer` must not
  substitute a number. Note the coupling to Recommendation 2: routing generation
  through `JobRunner` would make its 120 s hard budget
  (`repo-intel/constants.ts:47`) the de-facto answer instead, which is exactly
  why this plan runs the call inline. Same discipline as SPEC-01's Q7.
- **Execution mode is assumed, not confirmed.** `AskUserQuestion` is not
  available inside a subagent, so multi-agent was recorded per the user's stated
  expectation. If the answer is single-agent, `Scope` and `Explicitly out of
  scope` need amending and per-item test-writing plus a final self-verification
  item added — before `implementer` starts, not after.
- **Recommendation 2 (inline vs `JobRunner`) is a plan decision the Spec
  delegated, and it is reversible but not cheaply.** Moving to a job later adds a
  job kind, a status endpoint and a client polling hook. If the product owner
  wants a visible progress bar with per-stage detail rather than a spinner, decide
  that before WI9, not after.
- **AC-27's guard is in-process only.** A `Map<repoId, Promise>` holds for a
  single API process — which `server/AGENTS.md` already documents as an
  assumption (`reapStaleRuns()` on boot "assumes a **single** API process — no
  multi-replica safety"). Under multiple replicas two users could still each pay
  for a generation (E-13). Recorded rather than solved: a DB-level lock is out of
  scope for this iteration, but `plan-verifier` should see the limit stated.
- **`onboarding.system.md` is edited under D-6/Q7 permission, and the Spec
  quotes its line numbers.** After WI5 rewrites lines 22-26, the Spec's citations
  (`onboarding.system.md:8-9,11-12,22-26,42`) drift. That is expected and not a
  reason to leave the file contradicting the five canonical kinds — but
  `doc-writer` should note the drift rather than "fix" the Spec, which is
  human-authored and out of every downstream agent's write scope.
- **Nothing found stale in `AGENTS.md`/`INSIGHTS.md` while planning**, with one
  near-miss worth flagging to `implementer`: `server/AGENTS.md:21-23`'s module
  list ("repos, pulls, polling, reviews, agents, repo-intel, settings,
  workspace") has not been updated for `skills`, `conventions`, `smart-diff`,
  `blast` or `project-context` either — it reads as an illustrative list, not an
  exhaustive one, so adding `onboarding` there is `doc-writer`'s call, not a
  correction this plan mandates.
